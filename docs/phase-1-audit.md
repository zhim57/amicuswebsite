# Phase 1 repository assessment and implementation audit

Date: **2026-09-11**. Scope: repository changes for the Amicus Shipping LLC corporate website and read-only checks of public application destinations. No production deployment, DNS change, PM2 restart, purchase, account registration or email delivery was performed.

## Original architecture

The site was a Node.js/Express application with server-rendered EJS pages at `/` and `/resources`, using npm, a lockfile, Webpack and Sass. Its home page presented an application directory. An additional static homepage and a publicly served `public/deleted_code` directory retained older portfolio, commerce, legal and utility pages. Templates loaded Bootstrap, Font Awesome, Google Fonts, jQuery and Popper from CDNs.

There was no database, authentication, SMTP integration or application session cookie. The inquiry interface opened a `mailto:` draft and used an editable six-hour localStorage throttle; it did not send email. Multer accepted anonymous uploads, including HTML, saved them to `UPLOAD_DIR`, exposed them at `/uploads`, and returned filenames from `/files`. Resources were generated by reading that directory.

The deployment workflow pulled `master` into `/var/www/amicusshipping`, installed packages and restarted PM2 process `amicusshippingllc`. It had no preceding application validation or frontend build. The actual server default was `3016`, despite the old README saying `3000`. No Nginx configuration or complete production-infrastructure definition was present.

## Current architecture and presentation

- `server.js` provides a testable application factory, routing, redirects, reviewed static serving, indexing and error responses. `src/server/contact.js` and `security.js` isolate form/security behavior.
- `src/site-data.js` centralizes company presentation, authoritative external destinations, navigation, metadata and curated resources. EJS remains server-rendered.
- Public pages are `/`, `/solutions`, `/seafarers`, `/operators`, `/resources`, `/about`, `/contact`, `/privacy`, `/terms` and three explicitly registered resource articles.
- The homepage establishes the maritime proposition, three solution families, a substantial eSIM section, distinct audience paths, an Amicus introduction, resources and differentiated purchase/inquiry actions.
- Shared header/footer, Sass and a small local browser script replace the old presentation. Existing imagery is reused; ownership/licensing and suitability still need owner review.
- The page registry drives titles/descriptions and sitemap entries. Templates add canonical/social metadata, theme color, favicon/touch icon, Organization data and breadcrumbs without invented ratings or credentials.
- Useful legacy content URLs permanently redirect to relevant replacements. Unknown URLs receive a professional 404; unrelated removed content is not blanket-redirected to the homepage.
- Legacy schedule/rate source and build entries remain. The corporate pages do not load them as new features or claim their external API contracts are current.

## Security, privacy and deployment boundaries

There is no database, authentication, session-cookie workflow or SMTP transport. Contact inputs are received for validation and rendering an encoded draft; inquiries are not persisted or automatically delivered. Contact tests validate preparation/rejection/throttling, not an inbox or phone email application.

`UPLOAD_DIR` remains configurable and files remain untouched. `PORT` retains `3016`. `TRUST_PROXY` defaults to false; other values require a verified topology and control of direct Node access. Set one random `CONTACT_FORM_SECRET` of at least 32 characters across workers/restarts. Without it, process-local secrets can invalidate forms on another worker or after restart. The rate limiter remains per process even with a shared token secret.

Production CSP permits reviewed assets and the existing analytics origin, with nonces for JSON-LD. The app adds nosniff, frame restrictions, referrer/permissions policies and production-only HSTS. It does not configure TLS, Nginx, firewall rules or shared rate limiting.

Umami loads only in production unless `ANALYTICS_ENABLED=false`. Hooks send allowlisted events and a pathname, not inquiry text, email-draft URLs or query strings. Draft preparation is not a delivery conversion. Cross-subdomain attribution, retention and production privacy settings require separate verification.

The GitHub workflow validates before deployment, pins actions, checks the VPS revision against the triggering commit, installs build dependencies with `npm ci --include=dev`, builds, and restarts/saves the existing PM2 process. **No deployment was performed.** Inspect Nginx/reverse-proxy aliases for `/uploads`, `/files`, `/deleted_code` and repository-root delivery that could bypass Express, then verify public retirement/header behavior after deployment.

## Validation

Recorded verification during Phase 1:

- **62 Jest backend tests passed**, covering routes, metadata, retirement, retained storage and contact/security behavior.
- **5 Playwright tests passed**. All 12 public pages rendered and passed the selected axe WCAG 2 A/AA, 2.1 AA and 2.2 AA rules. Automated rules do not constitute a complete accessibility certification.
- **49 overflow checks passed:** seven principal routes at widths 320, 375, 390, 430, 768, 1024 and 1440 pixels.
- Browser checks included mobile menu/keyboard Escape, JavaScript-disabled usability, email-draft preparation, 404 recovery and absence of page errors.
- Desktop home, mobile home, mobile contact, desktop Solutions, About and Resources screenshots were inspected under `.qa/`.
- Dependency audit reached zero reported vulnerabilities. External links were checked with safe GET requests, not purchases or authenticated actions.

Reproducible PowerShell commands:

```powershell
npm.cmd ci
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test -- --runInBand
npm.cmd run build
npm.cmd run check:links
npm.cmd audit
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Get-Location) '.qa/browsers'
npx.cmd playwright install chromium
npm.cmd run test:browser
```

Keep `PLAYWRIGHT_BROWSERS_PATH` the same for installation/execution, including in a new terminal. The browser runner owns a fresh server on a random loopback port and closes it after testing. Lint enforces undefined/unused-variable and safety rules across current code and both test suites. The strict TypeScript `checkJs` pass covers the new browser script and central data; legacy JavaScript is intentionally excluded. Internal-link checks cover rendered pages/assets/known anchors. CI runs lint/typecheck/Jest/build/internal links, installs Chromium with `--with-deps --no-shell`, and runs browser tests. Emulated viewports do not prove physical-device behavior, Core Web Vitals, email delivery or production infrastructure health.

Final verification: production build completed without warnings; lint, strict scoped typecheck, 62 backend tests, 5 browser tests (11.2 seconds), and 13-page/18-destination internal-link checks passed. Both full and production-only npm audits reported zero vulnerabilities. The rebuilt corporate assets are approximately 14.7 KiB CSS and 1.09 KiB browser JavaScript before transfer compression, plus the existing 55.6 KB hero photograph. These sizes do not establish field Core Web Vitals. Git whitespace checks passed. PowerShell needed the workspace `.npm` cache for package writes; an initial Playwright shell-server teardown stalled on Windows, resolved by the isolated server runner included in the repository.

Implementation references: [Express production security guidance](https://expressjs.com/en/advanced/best-practice-security/) and [Umami tracker functions](https://docs.umami.is/docs/tracker-functions). Store compatibility links use the current [Amicus eSIM help page](https://sim.amicusshippingllc.com/help).

## Remaining risks and uncertainties

1. Production proxy aliases/headers and actual indexing removal remain to be verified; historical uploads, logs and search caches require private review.
2. Mailbox ownership, email-app behavior and inquiry delivery are unverified. A server email transport is separate work.
3. Existing Square fulfillment, global1tel billing availability and historical rewards balances/migration need owner/application review.
4. Company biography, credentials, business contacts and photo rights require owner-approved material; no testimonials or statistics were fabricated.
5. Corporate privacy/terms describe implemented behavior but need owner/legal review alongside actual hosting, analytics and email retention.
6. Real device usability, field performance, cross-subdomain attribution and external authenticated workflow health need deployment/customer verification.

## Ranked Phase 2 recommendations

1. **Verify production security after deployment.** Inspect proxy aliases, trusted proxies, TLS, secret provisioning and public retirement responses; privately review retained uploads/indexing history.
2. **Exercise real customer journeys.** Test seafarer phones, email-draft handling, SIM purchase/setup guidance and controlled crew registration.
3. **Resolve existing-customer continuity.** Confirm Square recharge/add-on fulfillment, the old billing path and rewards migration policy; provide one clear support route.
4. **Strengthen factual trust content.** Obtain approved company history, relevant credentials, public business details and owned/licensed photography.
5. **Improve commercial inquiry delivery if needed.** Evaluate a maintained mail transport with observable outcomes and shared abuse controls, keeping personal details out of analytics/logs.
6. **Measure the deployed site.** Establish Search Console, Lighthouse/field performance and Umami conversion baselines; verify cross-subdomain attribution and retention.
7. **Review resources with maritime expertise.** Check IFIA terminology/question currency and strengthen useful guides; add authenticated publishing only when needed.
8. **Refine accessibility and presentation from feedback.** Prioritize real device friction, image optimization and a purpose-made sharing image before speculative animation or dashboards.
